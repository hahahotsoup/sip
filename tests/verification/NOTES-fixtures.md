## ⚠️ 事故记录：不要用 PowerShell 改源文件（一次真实的文件损毁）

**2026-09-25，`AiReading.cs` 被 `Get-Content -Raw` + `Set-Content -Encoding UTF8` 毁掉。**

链条：这台机器的 ANSI 代码页是 **GBK(936)**。PowerShell 5.1 的 `Get-Content -Raw` 按 ANSI 解码，
于是文件里每个 UTF-8 中文字符被当成 GBK 字节对读成两个字（`══════` → `鈺愨晲鈺愨晲`），
`Set-Content -Encoding UTF8` 再把这份 mojibake 写成 UTF-8 存回去。

**比 mojibake 更麻烦的是换行被吞**：`—`(E2 80 94) 后面紧跟换行时，GBK 会把 0A 当成
那个双字节序列的第二字节吃掉 → 换行消失 → **下一行代码被粘到注释行末尾**。
结果文件从 928 行变成 940 行，但其中若干"行"里塞了 3~5 条语句。

**为什么救不回来（三条，都实测过）**：
1. 该文件**未被 git 跟踪**（`?? AiReading.cs`），没有历史可回滚。
2. 逆向不可行：PowerShell 走的是**替换式回退**（不是抛错），丢失的字节是真丢了 ——
   用 Python `errors="replace"` 复现链条时直接抛 `UnicodeDecodeError`，
   说明"逆向"根本无从下手（`probe_gbk_chain.py` 的结论）。
3. 我随后**又叠了两个修补脚本**，往文件里写进了 343 个 NUL、行数涨到 1679 ——
   比原始损坏更糟。教训：**第一次修复没验证通过时，不要在同一份产物上继续打补丁**，
   先回到已知状态的副本。

**判定"代码是否完好"的正确方法**（当时靠它确认了 C# 语句没坏）：
代码语句在 ASCII 区间，恒可逆。统计"含损坏字符**且**含 C# 语句特征"的行数 ——
实测 **0**，所以受损的只有注释。诊断脚本已清理（它们本身是一次失败实验），
结论留在这里：**下次先做这个判定，再决定是"修注释"还是"重建文件"**。

**铁的纪律**：改源文件只用 read/write/edit 这类按 UTF-8 处理的文件工具。
**任何** PowerShell 的 `Get-Content`/`Set-Content`/`-replace` 都不许碰 `.cs`/`.json`/`.md`/`.js`。
（`languages/*.json` 那次我改对了 —— 因为用的是 node 脚本，不是 PowerShell。）

### 后来真的修回来了（**方法比事故更值得记**）

2. **占位符是可判定的**。`<<XX>>?` 的每个 XX 都是被 GBK 吞掉前 1~2 字节的 UTF-8 序列，

   这类损坏**编译不一定报错**（`//` 吞到行尾 → 代码静默消失），所以：
   - 先靠编译器抓语法错（它把 300+ 处收敛到 6 处）

4. **确认"代码没坏"的正确判据**：代码在 ASCII 区间，恒可逆；受损的只有注释。

1. `chapter_db_diag.mjs` —— 只读**数据库副本**（`rss.db` + `-wal` + `-shm` 一起复制，
   绝不碰活库），拿 `Chapters` 行的 `Ord`/`ChapterId`/`Title`。
2. 同一脚本里用 Python `zipfile` **独立解包 EPUB**，搜关键词落在哪个 spine 文件。

两侧一撞就定死了：`长顺` 只在 `text/part0005.html` → 那是 `epub:5` = `ord 3`「正文一」；
而面板报"第 1 章"（`epub:0~front`，front matter，live 取回 `text` 长度为 **0**）。
根因是前端把**自己切节的序号**当成了章节号送出去，而服务端 `FindChapter` 只认精确 id 与 `#<ord>`。
契约记为 §12.1-A45，验收 A46。

**顺带一个未解疑点**（记下来免得丢）：`epub:0~front` 在目录里标称 `charCount=326`，
实时取回是 **0**。那个陈旧计数值可能是"抢答第 1 章"的一环，**尚未单独验证**。

## 真实安装（`E:\我的sip`）升级记录


- `Web server failed to start: 拒绝访问。` 的成因：`sip_settings.json` 里 `"WebHost": "0.0.0.0"`，
  非回环绑定要走 `http://+:8777/`，Windows 上非管理员进程需要 urlacl 保留。
  现在 `netsh http show urlacl` 里已有 `http://+:8777/ user=\Everyone`，**绑定已可用**
  （探针实测：`127.0.0.1:8777` → code 5，`+:8777` → OK，`0.0.0.0:8777` → code 50「不支持该请求」）。
  所以那次报错是**保留生效之前**的事；不需要改端口。
  ⚠ 别被 `code 5` 误导成"端口被占用"：`IsLoopbackHost` 分支会给出 `netsh http add urlacl` 提示，
  非回环分支才走 urlacl 文案，两条提示对应两种完全不同的处置。
