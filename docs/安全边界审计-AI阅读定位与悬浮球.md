### 2.2 写操作闸门与 CSRF
- `Web.cs:218-225` — 非 GET/HEAD/OPTIONS 一律先过 `WebOriginOk`。
- `Web.cs:784-805` — `WebOriginOk`：Origin host 必须等于请求 Host，且必须是回环或**IP 字面量**（刻意不认域名 → 防 DNS rebinding）。
- `Web.cs:484-508` — `WebWriteAllowed(res, what)`：Simon 挡位 ≥2 时**拦掉一切写操作**并回 403 `SIMON_BLOCKED`。
- **审计含义**：（a）会话/对话历史的**删除与清空**必须是写操作并过 `WebWriteAllowed`（**这一条从未变动过**，无论第 2 条怎么裁）；（b）**聊天问答本身是否过闸由 §8 第 2 条裁定，此处不复述** —— 该点裁决反复过 5 次（宽松 ↔ 严），本文档把结论与判据集中在 §8，避免同一事实在两处各写一版而失同步。

### 4.2 第 2 条（输入边界）
- 章节标识：`章号 = 0 / -1 / 1e9 / 2147483648 / "1.5" / "1,2" / 空 / 超长(10 万字符) / Unicode 全角数字 / `..` / `%00` / `%2e%2e%2f` / 大小写混写`
- 页码：同上 + 单页 PDF 的 `page=2`、页数缺失（`PageCount` NULL）时的越界行为

- 查询串：关键词长度上限、`LIKE` 通配符 `%`/`_`、SQL 注入字符（应走参数化）
- 请求体：聊天请求的 body 上限 —— **已核实：共用读体函数 `ReadBodyAsync`（`Web.cs:991-996`）没有任何上限**，见 §5-B5；因此「新端点是否自带上限」就是本条的实测点（不设即按 B5 同源问题记发现）。另测超长划词（1 MB 级）与超长提问的实际行为。

## 5. 本轮顺带登记：基线既有弱点（B 系列，非本次新增，但新代码极易复用）

> 登记理由：这三处都在「新代码最可能复用的公共函数」上（资产围栏、错误回显、上传体积闸），因此它们不只是历史问题，而是新代码的**默认继承风险**。

**B1｜资产围栏缺少目录边界（低，纵深防御）**
- 位置：`Web.cs:3440-3441`
- 现状：`root = Path.GetFullPath(ImportedDir())` → `root` 形如 `<dataDir>\imported`（**无尾分隔符**，`sipcore.cs:665`），判定用 `full.StartsWith(root, OrdinalIgnoreCase)`。
- 影响：兄弟目录 `<dataDir>\imported<任意后缀>\x.png` 会通过前缀判定，被 `/api/imports/{id}/asset` 原样读出（`Web.cs:3452-3459` 不校验扩展名，还会按扩展名给 `Content-Type`）。前提是本机确实存在该目录与文件——所以严重度是低；但**若新代码用它读章节资源/附件，等号右边会变成用户可控范围更大的文件集**。
- 期望修法（不在我的权限内，仅给出）：把判定改成 `root + Path.DirectorySeparatorChar` 前缀，或比较 `Path.GetRelativePath(root, full)` 不以 `..` 开头。

**B2｜异常消息原样回给前端（低-中，信息泄漏）**
- 位置：`Web.cs:465-469`（路由级 catch，`message = ex.Message`）、`Web.cs:3308`、`Web.cs:3507`
- 影响：任何未捕获异常的实现细节（含**绝对路径**、文件系统结构、第三方库报错文本）直接进入 JSON 响应，被浏览器与任何已认证的本机进程看到。
- 期望：新代码的 `catch` 一律返回固定文案 + 错误码，细节只进服务端日志。这条也是第 3 条的判定口径：**新接口若照抄 `ex.Message` 回显，就按发现处理**。

**B3｜上传体积仅校验 `Content-Length`（待实测，未定级）**
- 位置：`Web.cs:3262-3267`：`if (req.ContentLength64 > maxBytes) → 413`，之后 `await req.InputStream.CopyToAsync(fs)`（`Web.cs:3282-3283`）落临时文件。
- 疑点：`Transfer-Encoding: chunked`（无 Content-Length）时该判定是否还被触发，需要起隔离实例实测；现在**不下结论**。EPUB 上传是新 harness 的入口，这条我会在 t6 正式开工时优先打。

**B4｜`async void` handler 在 `await` 之后的异常会逃逸成进程终止（机制确定 / 可达性待实测）**

> 这条与本次新增功能无关，但有**两重**登记理由：① 它是 A1 的既有实例（captain 认可保留，供后人看到）；② 它正是新 SSE handler 最容易复制的形状。

- **机制（确定，有代码证据）**：`Web.cs:465-469` 的路由级 `try/catch` 只兜住**同步**抛出。`async void` handler 在首个 `await` 之后的异常不会回到那里，而是落到 ThreadPool 的未处理异常 → **进程终止**（不是 500、不是日志里一条错误）。
- **已逐行核过、方法体内无顶层 try 的实例**（异常只需来自任意一次 `WriteJson`/`ReadBodyAsync`）：
  - `Web.cs:944-959` `HandleReadingProgressSet`（`await` 在 946，`WriteJson` 在 951/958）
  - `Web.cs:1895-1938` `HandleArticleFulltext`（**只有局部 try** 包住 1900-1910 的读体；1935/1937 的 `WriteJson` 在 try 之外 —— 这正是 A1 指出的「局部 try 形状」）
  - `Web.cs:3915-3960` `HandleSimonLevel`（`await` 在 3917，全程无 try）
  - `Web.cs:3981-3992` `HandleTelemetrySet`（`await` 在 3984，全程无 try）
  - `Web.cs:4103-4124` `HandleInsightsInterval`（`await` 在 4106，全程无 try）
  - （全仓共 **23** 个 `static async void Handle*`；上述 5 个是我本轮逐行读过的，其余待 t6 全量过一遍。）
- **可达性（未验证，不下结论）**：是否真能杀掉进程，取决于「客户端中途断连时 `HttpListenerResponse.OutputStream.Write` 是否抛异常」。这一步我会在 t6 用隔离实例实测：发起请求后立刻断连（尤其打长耗时的 `/api/articles/{id}/fulltext`），观察服务进程是否存活。
- 期望形态（也是我给新 SSE handler 的要求）：handler 返回 `Task` 而非 `async void`，函数体**整体** try/catch（含每个 `await` 之后与 finally 里的 flush/close）。

**B5｜请求体无任何大小上限，且存在一条「未认证可及」的路径（机制已核实，影响量级待实测）**

- **机制（已核实，读码即证）**：`Web.cs:991-996` `ReadBodyAsync` 只做 `await sr.ReadToEndAsync()`，**没有任何长度上限**（既不查 `ContentLength64`，也不做分块累计上限）。凡调用它的 handler 都会把整个请求体一次性读成 `string`（UTF-16），即 N 字节 body ≈ 2N 字节托管内存，且并发请求各自独立。
- **未认证可及的路径（精确条件，已核实）**：`POST /api/login` 的分派在 `Web.cs:250-252`，位于 `/api/*` 认证闸门（`Web.cs:341`）**之前**；`HandleLogin` 在 **密码模式**下会先 `await ReadBodyAsync(req)`（`Web.cs:817`）再判口令。因此**密码模式下，一个未认证请求就能让服务端无上限地分配内存**（`StreamReader` 读完才进入限流判断 `Web.cs:830`）。配套事实：`Web.cs:788` 的 `WebOriginOk` 对**不带 Origin/Referer** 的请求直接放行，所以「不带 Origin 的本地进程/脚本」不受 CSRF 检查阻挡；默认绑定 `127.0.0.1`，但 `WebHost` 可配置为局域网可达。
  - 补充：**无密码模式**下 `HandleLogin` 在读体之前就返回（`Web.cs:809-816`），所以那条路径不存在；该漏洞只在密码模式下成立。
  - 补充：恶意**网页**难以利用（`Content-Type: application/json` 会触发预检 `OPTIONS`，而路由表里 `/api/login` 只匹配 POST，预检落到末尾 404 且无 CORS 头 → 浏览器拦下真实 POST）。所以威胁面是**本机任意进程 / 局域网（若配了 WebHost）**。
- **量级（待实测，不下结论）**：具体多少字节能压死进程取决于机器内存与 GC；t6 用隔离实例逐步加大 body，记录进程内存与存活情况。
- **与新功能的关系（为什么现在登记）**：聊天请求要收下用户的粘贴内容，body 天然比其他 JSON 接口大，最容易出现「把上限调大或干脆不设」；而它默认会复用同一个 `ReadBodyAsync`。判定口径（**已与 harness-eng 对齐，见 §8-A4**）：**新 chat 端点必须自带上限**，分块累计、到限即拒（413 + `BODY_TOO_LARGE`）；**字段级截断（4000 / 1500 字 + `truncated`）不能替代 body 上限** —— 截断发生在读完之后，挡不住内存；反过来说，字段截断也不得被 body 上限吃掉（10 万字提问必须 200 + `truncated`，不得 413）。
- 期望修法（不在我的权限内，仅给出）：给共用读体函数加字节上限（例如 1 MB 级，按用途可调），超限立即回 413 且**不分配**对应内存（读流时分块计数即可），同时补 `ContentLength64` 预检。

### 审计侧追加的 3 条判定要点（已同步 harness-eng）
- **A1｜`async void` 的异常不会回到路由级 catch。** `Web.cs:465-469` 只兜住**同步**抛出；`async void` handler 在首个 `await` 之后的异常会落到 ThreadPool 的未处理异常 → **进程终止**，而不是一条 JSON 错误。因此第 3/4 条的「自捕获」是**可用性**要求，不只是防泄漏：整个函数体（含每个 `await` 之后）都必须在 `try` 内。既有 `HandleArticleFulltext`（`Web.cs:1895`，`async void` + 局部 try）就带这个潜在洞 —— 登记为基线观察，不计入新代码缺陷。
- **A2｜断连检测本质是「写失败驱动」。** HttpListener 没有断连回调，可靠信号是 `OutputStream.Write/Flush` 抛 `IOException`。取消链路必须挂在这个失败上，并配心跳间隔保证检测及时（否则长静默期内的断连要等到下一次写才发现）。
- **A3｜分隔标记可被内容伪造。** 若用固定标记包裹不可信正文，正文里出现同一标记即可提前闭合包裹。要求：对不可信内容里的分隔串做剥离/改写，或改用每请求随机 nonce。我会用「正文含完整分隔标记」的语料实测。
- **A4｜请求体上限 vs 契约的字段截断（已与 harness-eng 对齐，两者不是一回事）**
  - **HTTP body 总上限**（内存护栏，即 §5-B5 要求的落点）：**2 MiB**（**实现方 2026-09-25 定**，从最初提的 1 MiB 上调 —— 见下方窄边界）；**分块累计计数、到限即拒**（不先读完、不只信 `ContentLength64`；chunked 同样受管）→ **413 + `BODY_TOO_LARGE`** + **`limit`（字节数）**固定文案。
  - **字段级**（prompt 体积控制，**是截断不是拒绝**）：`question` 截到 **4000 字**、`selection` 截到 **1500 字**，并置 `truncated:true` → **仍回 200**。
  - **依据（我独立核对过契约原文，不是转述）**：`docs/AI阅读定位-契约.md` **§9-21** 表第 21 行「超长粘贴（10 万字提问）→ 服务端截断到 4000 字并 `truncated` 标注，**不**因体积拒绝」（引用时点：我读到的是 `:1223` 版；**契约行号会漂，按"§9-21"条目号引用**）；`selection.text` 服务端最多保留 1500 字符。
  - **为什么是 2 MiB 而不是 1 MiB（我算出的窄边界，实现方采纳）**：10 万字中文 UTF-8 ≈ 300 KB，远在两者之下；**但**若客户端把非 ASCII 做 **`\uXXXX` 转义**（6 字节/字）≈ 600 KB，而粘贴**星平面字符**（代理对）再转义可到 **~1.2 MB > 1 MiB** → 那就会「因体积拒绝」，与 §9-21 字面冲突。**2 MiB 消掉这条矛盾，同时仍是有界内存。**
  - **判定口径**：body 超 **2 MiB** → 413（且**不先读完**）；10 万字提问 → **200 + `truncated:true`**（**不得** 413）；无上限 / 仅信 `ContentLength64` → 按 §5-B5 记发现。
  - **不先读完的实证方式**：连发多个「实际远超上限」的 chunked 请求，看**进程工作集不随 body 线性抬升**（实现方已承诺这是**显式提前退出**，不是读完再判）。
  - **`limit` 已是契约要求（非"建议"）**：413 的 payload 带 **`limit`（字节数）**，与既有 `SIMON_BLOCKED` 带 `level` 同风格；requirements 已入契约并给了验收 **A42**（且**与导入文件的 `TOO_LARGE`（512 MB）分开** —— 一个是请求体、一个是文件，不许混用一个码）。契约 §3.6 里连动因都记的是我那条：**「否则『有上限』这条边界无法被断言（只能断言 413 出现了，不能断言上限是多少）」**。
  - **我的测法改为「自描述式」（契约只要求"可断言"，未固定数值）**：契约**不钉具体上限值**（数值属实现选择），所以我**不硬编码 2 MiB**，而是：① 先发一个超限请求，**从 413 payload 读出 `limit`**；② 再发 `limit` 字节的请求 → **不得 413**；③ 发 `limit + 1` 字节 → **必须 413**。这样即使实现方日后调整数值，我的断言依然成立；也顺带证明 `limit` 与实际判定**一致**（字段若撒谎，②③会互相矛盾）。
